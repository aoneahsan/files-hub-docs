Password manager

FilesHub keeps logins for your projects and lets your own code manage them over the API. Each entry looks like an entry in iCloud Passwords: a title, its websites, a username, the password, an optional verification-code setup key, notes, tags and a favourite flag.

Availability

Added in backend 2026.10.23.5. Check what is running with GET https://fileshub.zaions.com/api/version (backend_version); on an older backend every /api/v1/passwords route answers 404.

Read next: Quick start · Access and scopes · Endpoint reference · Using the dashboard

What an entry holds​

FieldTypeNotes
kindlogin (default), wifi or noteSince 2026.10.24.2. A Wi-Fi network keeps its name as title, its password and wifi_security (wpa3, wpa2, wpa, wep, open). A secure note has a title and encrypted notes and no password.
titlestring, required, ≤ 191What you call it: "Domain registrar".
websiteslist of strings, ≤ 20Normalised to https://host[/path], de-duplicated. registrar.example.com becomes https://registrar.example.com.
usernamestring, ≤ 191The login name or email. Stored as plain text so you can search it.
passwordstring, required (except for a note), ≤ 1,024Encrypted at rest. Never returned except by reveal.
totp_secretstringThe verification-code (two-factor) setup key, as base32 (JBSWY3DPEHPK3PXP…) or the whole otpauth:// link. Encrypted. FilesHub then returns the current code on reveal, like an authenticator app; a link's digits (6–8), period and algorithm (SHA1, SHA256, SHA512) are followed.
notesstring, ≤ 10,000Encrypted at rest; returned with the entry's details.
tagslist of strings, ≤ 20, each ≤ 40For filtering: ["domains", "billing"].
is_favoritebooleanFavourites sort first.

FilesHub adds:

FieldMeaning
idThe entry's public id (26 characters). Use it in every URL.
project_idThe FilesHub project the entry belongs to.
strength{score, label}: zxcvbn score 0–4; label weak, fair, strong or very strong.
reusedtrue when another live entry in the same project has the same password. Computed on single-entry answers; null in lists. FilesHub compares a keyed fingerprint and never decrypts a password to do it.
has_verification_codeWhether a setup key is stored.
compromisedtrue when the password appears in a known data breach (Have I Been Pwned), false when it does not, null until it has been checked. Only the first 5 characters of the password's SHA-1 hash ever leave FilesHub. Checked on save and again about weekly.
breach_checked_atWhen that check last ran.
purges_atFor an entry in Recently Deleted: when it is removed for good (30 days after deletion).
owner_scopeown or admin — who can reach it. See Access and scopes.
created_viaapi or dashboard.
password_changed_at, last_revealed_at, created_at, updated_at, deleted_atISO 8601 times.

Password history. Changing a password keeps the old one: the last 10 earlier passwords, encrypted, returned by reveal with history: true.

Recently Deleted. Deleting an entry moves it to Recently Deleted. It can be restored, or removed for good with a second, explicit call.

Who can reach which password​

Every API key starts with no access to the manager. You give a key one of two scopes:

ScopeThe key can reach
none (default)Nothing. Every password route answers 403.
ownOnly the entries this key created, in its own project. No other key sees them through the API — not even an admin key.
adminEntries created by admin keys or in the dashboard, in the key's project. Never an own key's entries.
admin + every projectThe same, across all projects.

And you can narrow either scope to some of five abilities: list, reveal, create, update, delete. Full rules: Access and scopes.

                    ┌────────────── project A ──────────────┐   ┌──── project B ────┐
own key K1   ──────▶│ entries K1 created                    │   │                   │
own key K2   ──────▶│ entries K2 created                    │   │                   │
admin key    ──────▶│ entries from admin keys + dashboard   │   │                   │
admin key + every project ──────────────────────────────────▶│ admin + dashboard │
                    └───────────────────────────────────────┘   └───────────────────┘

An entry a key cannot reach answers 404 Not found, the same as an id that does not exist, so a key can never learn that someone else's password is there.

Security model​

  • Passwords, setup keys, notes and the password history are encrypted with a key used only for stored secrets (since 2026.10.24.1; see Security).
  • Answers from /passwords are sent with Cache-Control: no-store, so no browser or proxy keeps them.
  • At most 30 reveals a minute per key (429 after that).
  • Give a password key an address allowlist (allowed_ips, below) so a copied key is useless anywhere else.
  • Every create, change, delete, restore, permanent removal and reveal is written to the audit log with the entry id, the key and (for changes) the field names. A value is never logged.
  • A key's password scope can only be granted by you in the dashboard, or over the Management API by a token holding can_manage_passwords.
  • 🔴 Use a password-scoped key from a server only. Never put it in a browser or mobile bundle: anyone holding the key can do what its scope allows. Prefer a separate key for passwords, with only the abilities it needs (a read-only integration gets list and reveal, nothing else).
  • Recently Deleted keeps an entry for 30 days, then it is removed for good.
  • If an entry can no longer be decrypted (for example after the application key was rotated), reveal answers "password": null, "unreadable": true instead of failing.

Plans​

Your own (internal) projects use the password manager without a plan. An external project answers 402 until a password-manager plan is available for it; see pricing.
